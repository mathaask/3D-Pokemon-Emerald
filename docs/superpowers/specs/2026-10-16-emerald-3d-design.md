# Emerald 3D — Design Spec

Date: 2026-10-16
Status: approved under "full freedom" delegation from the user (auto mode)

## 1. Intent

The user supplied a Pokémon Emerald (BPEE, rev 0, SHA-1 `f3ae0881…`) ROM and asked for
"a full working 3D game based on this ROM" with good visuals and *all* built-in mechanics
and storylines, and wants to be impressed.

Success criteria:
- The entire game is playable start to finish: intro, new game, every map, every script,
  battles, menus, saving, Pokédex, berries/clock features, Battle Frontier.
- The overworld is presented in real 3D (perspective camera, depth, lighting, shadows,
  weather) — not a flat texture on a plane.
- Battles are presented as a 3D scene.
- The repository contains **no Nintendo assets**: everything visual/audio is decoded at
  runtime from the user's ROM.

Assumptions (user did not specify): a browser app is acceptable (Vite dev server, Chrome/Edge);
keyboard + gamepad input; English ROM only.

## 2. Core decision: emulated logic + replacement renderer

Re-implementing Emerald's ~1500 script commands/specials, battle engine, and every UI by hand
cannot reach "all mechanics and storylines". Instead the game's **original code runs in a
GBA emulator written for this project**, and a **new 3D renderer reads the game's live state
from emulated RAM** (addresses from the pokeemerald symbol table for this exact build) and
draws it in 3D. This is the "HLE renderer" pattern used by modern N64/GBA remaster projects.

```
            ┌───────────────────────────── browser main thread ───────────────────────────┐
 ROM file ─►│ GBA core (src/gba)  ──RAM/VRAM/PAL/OAM──►  Game state reader (src/game)      │
            │  CPU·Bus·PPU·APU·DMA·Timers·Flash·RTC        scene detect, map, objects,      │
            │        ▲ keys            │ audio              camera, weather, battle         │
            │        │                 ▼                          │                        │
            │   Input (src/input)   AudioWorklet           3D renderer (src/render)        │
            │                                              overworld · battle · 2D screens │
            └─────────────────────────────────────────────────────────────────────────────┘
```

## 3. Components

### 3.1 GBA core — `src/gba/` (pure TS, no DOM; runs in Node for tests)
- `cpu.ts` ARM7TDMI interpreter (ARM + THUMB), banked registers, IRQ/SWI exceptions,
  table-driven decode. Approximate cycle counting (sufficient: Emerald is VBlank-paced).
- `bus.ts` memory map: BIOS stub, EWRAM 256K, IWRAM 32K, IO, PAL 1K, VRAM 96K, OAM 1K,
  ROM ≤32M, Flash 128K. 8/16/32-bit access with GBA mirroring/rotation rules.
- `bios.ts` HLE BIOS: tiny ARM stub for the IRQ vector; SWIs implemented in TS
  (Div, Sqrt, ArcTan2, CpuSet, CpuFastSet, LZ77, RL, Huff, BgAffineSet, ObjAffineSet,
  IntrWait/VBlankIntrWait, Halt, RegisterRamReset, SoftReset, MidiKey2Freq, …).
- `dma.ts`, `timers.ts`, `irq` — immediate / VBlank / HBlank / sound-FIFO DMA.
- `ppu.ts` scanline renderer: modes 0–5, affine BGs, sprites (incl. affine), windows,
  blending, mosaic. Can also emit a **UI layer** (BG0 + windows only) for overlays.
- `apu.ts` PSG ch1–4 + DirectSound FIFO A/B, resampled to the host rate.
- `cart.ts` Flash 128K (Macronix ID, bank switch, sector erase) and S-3511 RTC over GPIO
  driven by the host clock.
- `gba.ts` facade: `runFrame()`, `setKeys()`, save/load flash, save states.

### 3.2 Game knowledge — `src/game/`
- `symbols.ts` generated by `tools/gen-symbols.ts` from `vendor/pokeemerald-sym`.
- `structs.ts` typed readers for MapHeader, MapLayout, Tileset, ObjectEvent, Sprite,
  BattlePokemon, Weather, PaletteFade… over the emulator's memory.
- `scene.ts` scene classification each frame via `gMain.callback2` / `inBattle`:
  `overworld` | `battle` | `screen2d` (menus, intro, title, Pokédex, …).
- `rom/` static decoders: tilesets, metatiles, map groups/connections, text charset.

### 3.3 Renderer — `src/render/` (Three.js, WebGL2)
- **Overworld 3D**
  - World mesh built per map from layout grid (current map + connected maps), cached per
    map; rebuilt on map change.
  - Tiles are decoded **in the fragment shader** from live VRAM + palette textures uploaded
    each frame → tile animations, weather tints and fades are inherited automatically.
  - 3D reconstruction ("un-projecting" the GBA's oblique 3/4 view): per-metatile class from
    behavior/collision/layer-type/pixels + per-cell elevation → floors at height, vertical
    faces for cliffs/walls, extruded building blocks with roof caps, standing cut-outs for
    trees and props, animated water surface. Heuristics are data-driven and tuned by
    rendering every map offline (tools) and inspecting the result.
  - Characters and field effects: every overworld sprite (from `gSprites`/OAM) becomes a
    camera-facing billboard decoded from OBJ VRAM, anchored at its world foot position,
    with soft shadows.
  - Camera: smooth follow, slight perspective tilt; user can orbit/zoom.
  - Lighting: day/night cycle from the RTC, dynamic sun shadows, lamp glow at night,
    sky dome, fog; weather (rain, thunder, snow, ash, sandstorm, fog, drought, underwater
    tint) from `gWeather` rendered as 3D particle systems.
  - UI overlay: GBA BG0/window layer composited on top (text boxes, menus, popups).
- **Battle 3D**: arena themed by battle terrain, battlers as billboards from their sprites,
  cinematic camera driven by battle state, move-animation sprites projected into the arena,
  HUD from the GBA healthbox sprites + text layer.
- **2D screens**: crisp upscaled GBA frame on a stylised panel over a blurred 3D backdrop.
- **Post FX**: bloom, tilt-shift depth of field, vignette, colour grading, FXAA.

### 3.4 Shell — `src/main.ts`, `src/ui/`, `src/input/`, `src/audio/`
- Auto-loads `/Pokemon_Emerald-.gba` from the dev server; drag-and-drop fallback.
- Keyboard + Gamepad API; on-screen help; settings (3D on/off, quality, camera, volume).
- Flash save persisted in IndexedDB/localStorage; quick save states; fast-forward.

## 4. Data flow per frame
1. Input → GBA keys. 2. `gba.runFrame()` (≈280 896 cycles), audio samples queued.
3. Scene detection. 4. Renderer pulls state (map/objects/camera/weather/battle) and
VRAM/PAL/OAM snapshots → draws 3D + overlay.

## 5. Error handling
- ROM missing/wrong hash → friendly loader screen with drag-and-drop.
- Unknown scene → fall back to 2D screen presentation (never a broken 3D view).
- Unimplemented SWI/IO → logged once, game continues.
- Renderer exceptions are caught per-frame; the 2D framebuffer is always available.

## 6. Testing
- Unit tests (vitest) for CPU instruction semantics, BIOS decompressors, flash, RTC.
- Headless Node runner (`tools/headless.ts`) runs the ROM with scripted input and writes PNG
  screenshots — used to verify boot, intro, new game, map transitions, battle.
- Headless Chrome (puppeteer-core) screenshots of the 3D renderer at fixed save states.
- Offline map atlas tool renders all maps in 2D and 3D-classified form to tune heuristics.

## 7. Out of scope
- Link cable / wireless multiplayer, e-Reader. (Game handles their absence gracefully.)
